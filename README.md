Сервис работает на бесплатном хостинге и засыпает после 15 минут без обращений. Первое открытие после сна поднимает контейнер и занимает до минуты — подождите, дальше страницы открываются за секунды. Решение кейса **«Космос: Без права на брак»** для РКК «Энергия» — интеллектуальный контроль качества деталей в космической отрасли.

Кейс звучит как задача распознавания, но постановка её исключает: на входе уже готовые результаты CV-модели Заказчика, собственные модели не требуются. Поэтому ядро решения — **прослеживаемость и доказательный разбор брака**. Результаты контроля, операции, операторы и оборудование сводятся в одну историю изделия. По ней система показывает, где дефект обнаружен, на каком этапе он мог возникнуть, на каком основании это видно и каких сведений не хватает. Решение по изделию принимает человек, и каждое решение — отдельная неизменяемая запись журнала.

## Как пользоваться

1. **Войдите под ролью.** В демонстрационном режиме логин совпадает с ролью, пароль — с логином:

   | роль | логин / пароль | главное на экране |
   |---|---|---|
   | контролёр ОТК | `controller` / `controller` | очередь проблем и решения по ним |
   | мастер участка | `master` / `master` | та же очередь, решения, отклонения станков на шкале |
   | технолог | `technologist` / `technologist` | сбои оборудования, причины, справочник станков |
   | руководитель производства | `manager` / `manager` | линии, блочный редактор, экономика |
   | администратор | `administrator` / `administrator` | типы станков, виды дефектов, роли, пользователи, журнал и ключи |

2. **Откройте линию** на экране «Производство». В центре — граф этапов: под этапом счётчики изделий за выбранный промежуток, над этапом красный круг с числом действующих проблем, нажатие на него открывает их список.
3. **Выберите проблему** в очереди слева, на шкале времени или в круге над этапом. Линия переносится в момент обнаружения, а под графом открываются изделие (слева) и проблема (справа): исходное сообщение анализатора, разбор системы и решения людей.
4. **Примите решение** с обязательным обоснованием. Эмуляция ведёт изделие дальше: после подтверждения дефекта операции — доработка и повторный контроль, после отклонения сигнала или закрытия — путь дальше по линии.
5. **Запустите поток** в **«Пульте эмулятора»** (кнопка в шапке): число изделий, время показа, вероятности дефектов по этапам и принудительные дефекты «изделие № → этап».

## Быстрый старт

Нужен только [uv](https://docs.astral.sh/uv/). Локально база — встроенный PostgreSQL, который поднимается сам, без установки в систему.

```bash
uv sync --extra dev
uv run uvicorn zero_defect.integration.emulator:app --port 8100 &
uv run uvicorn zero_defect.serving.api:create_app --factory --port 8000
```

Интерфейс — на `http://localhost:8000`, спецификация API — на `/docs`. При первом запуске сервис создаёт ключи в `var/keys` и наполняет базу: проверочные ситуации постановки и история двух линий за прошедшие смены. Линии сразу работают — по графу идут изделия.

В контейнерах (сервис, PostgreSQL и эмулятор внешней системы; пароль базы — в `.env`, который в репозиторий не попадает):

```bash
echo "ZD_DB_PASSWORD=$(openssl rand -hex 16)" > .env
docker compose up --build
```

Проверить, что всё сходится (то же запускает CI на каждый пуш):

```bash
uv run pytest
uv run ruff check src tests scripts
uv run python scripts/check_scenarios.py
uv run python scripts/check_generated.py
uv run python scripts/check_compat.py
uv run python scripts/export_openapi.py --check
```

Рабочий режим без демонстрационных данных — `security.demo = false` в `config/zero_defect.toml`: выбора роли на входе нет, пароль задаёт `uv run python scripts/keys.py password <пользователь>`. Публичный стенд Render — в [docs/render.md](docs/render.md); стенд на VPS, где проходила защита, закрыт, его настройка сохранена в [docs/deploy-vps.md](docs/deploy-vps.md). Ограничения защиты — в [docs/security.md](docs/security.md).

## Что проверено

- **8 из 8** обязательных ситуаций постановки сходятся с ожиданиями, записанными отдельно от входа ([docs/scenarios.md](docs/scenarios.md), `reports/metrics/scenarios.json`).
- **Нагрузочный прогон:** 2187 сообщений, из них 2100 уникальных. Один и четыре обработчика, перемешанный порядок и сбой связи с повторной доставкой дают одинаковый итог до хеша (`reports/metrics/load.json`).
- **Вмешательство в журнал** — изменение записи в обход приложения, удаление, пересчёт цепочки, отрезание хвоста — обнаруживается. Проверки идут на PostgreSQL и SQLite.
- **Эмулятор ничего не подсказывает разбору:** дефект, внесённый в этап принудительно, находится разбором как возникший именно там (`tests/test_lines.py`).
- **145 тестов** проходят на каждом изменении. Ещё 3 пропускаются намеренно: это варианты для SQLite проверки, которая имеет смысл только на PostgreSQL.
