# Архитектура

Документ описывает целевую систему и то, какая её часть реализована в MVP. Реализованное проверяется тестами и сценариями; то, что описано, но не реализовано, помечено явно.

## 1. Подход

**Модульный монолит на портах и адаптерах, поверх журнала событий.** Ядро содержит бизнес-правила и ничего не знает про HTTP, базу данных и внешние системы. Всё внешнее — транспорт, хранилище, внешние системы, телеметрия, криптографический профиль — подключается через узкий интерфейс и выбирается конфигурацией.

Почему так, а не микросервисы: постановка не требует выделять компоненты в сервисы, а у закрытого производства обычно нет платформы, на которой десяток сервисов дешевле одного процесса. Границы модулей проведены так, что любой из них выносится в отдельный процесс без правки ядра: связи между ними — вызовы через порты и подписка на события ядра.

Почему журнал событий: постановка требует хранить исходные события отдельно от изменяемых представлений и добавлять исправления и решения новыми записями. Журнал событий устроен ровно так. История изделия, карточки и показатели — производные представления, и их можно пересобрать из журнала в любой момент.

## 2. Конвейер

Пакет разделён по стадиям конвейера, а не по типам файлов.

```
          ┌── edge-агенты (буфер, подпись пакета) ──┐   ┌── эмулятор / 1С / Галактика / MES / КОМПАС ─┐
          ▼                                          │   ▼                                              │
  contracts/  JSON Schema → модели, документ, перечисления интерфейса                              │
          ▼                                          │                                                  │
  ingest/     проверка по контракту, повторы, опоздания, пропуски, карантин ◄── integration/ (задания)  │
          ▼                                          │                                                  │
  ledger/     журнал: только дописывание, шифрование, цепочка хешей, подпись пакета, якорь             │
          ▼                                          │                                                  │
  history/    история изделия: генеалогия, операции, паузы, повторы, проверки, станки                   │
          ▼                                          │                                                  │
  quality/    несоответствия: сигналы → карточка → решения людей                                        │
          ▼                                          │                                                  │
  analysis/   разбор обстоятельств, производственная аналитика, выгрузка OCEL                           │
          ▼                                          │                                                  │
  serving/    API, шина безопасности, интерфейс ─────────────────────────► integration/ (итоги) ───────┘
```

| модуль | ответственность | не знает о |
|---|---|---|
| `contracts` | схемы версий 1.0 и 1.1, сгенерированные модели, проверка совместимости | как событие будет использовано |
| `ingest` | проверка, нормализация к внутренней модели, идемпотентность, признаки опоздания | хранилище (пишет через `Ledger`) |
| `ledger` | хранение, шифрование, подпись, проверка целостности, ключи | смысл событий |
| `history` | история изделия, операции, связь станков с операциями | решения людей |
| `quality` | карточки несоответствий, статусы, правила решений | HTTP, внешние системы |
| `analysis` | этап возникновения, основания, альтернативы, показатели | HTTP, внешние системы |
| `integration` | порт внешней системы, адаптеры, исходящая очередь, сопоставление идентификаторов | правила разбора |
| `security` | пользователи, роли, токены, подпись источников, аудит | бизнес-правила |
| `storage` | схема базы, подключение к PostgreSQL или SQLite, защита журнала средствами СУБД | смысл данных |
| `lines` | линия как граф, эмулятор конвейера, статистика этапов, маршрут изделия, экономика | HTTP |
| `serving` | HTTP, представления, интерфейс | правила разбора |
| `simulation` | сценарии, генератор нагрузки, edge-агент, воспроизведение | — |

`service.py` — прикладной слой, через который всё перечисленное вызывается: `QualitySystem.ingest`, `decide`, `state`, `verify_integrity`.

## 4. Модель данных

Внутренняя модель — объекты и связи между ними; события — факты о них.

- **Изделие** (`item_id`, тип, происхождение: покупное или изготовленное, задание) — может входить в сборку и содержать компоненты.
- **Выполнение операции** (`operation_run_id`) — конкретное выполнение операции техпроцесса (`operation_id`) над изделием на участке, оператором, на оборудовании. Повторное выполнение получает новый идентификатор и ссылается на предыдущее через `previous_run_id`.
- **Наблюдение** — результат контроля на контрольной точке: обнаружены признаки, не обнаружены, оценка невозможна; с уверенностью и качеством наблюдения.
- **Несоответствие** — карточка, в которой связаны все наблюдения одного дефекта (объект, тип, зона). Идентификатор вычисляется из этого ключа, поэтому повторное наблюдение не создаёт второй карточки.
- **Решение** — действие человека по карточке с автором, ролью, обоснованием и временем.
- **Состояние оборудования** и **действие оператора** — обстоятельства, которые связываются с выполнением операции.

Полный контракт сообщений — [contracts.md](contracts.md), он порождён из схемы. Внутренняя модель (`ingest/model.py`) отделена от контракта: версии 1.0 и 1.1 приводятся к ней на границе приёма, поэтому версия контракта не смешивается ни с версией анализатора (`analyzer_version`), ни с версией приложения.

## 5. Правила обработки

**Порядок.** Порядок гарантируется в пределах изделия: события одного изделия раскладываются в один раздел (ключ — `item_id`, иначе `equipment_id`, иначе `source_id`). История строится сортировкой по времени возникновения, поэтому итог не зависит от порядка поступления — это проверено прогоном с перемешанным порядком ([scenarios.md](scenarios.md)).

**Повторы.** Доставка — «хотя бы один раз». Тот же `event_id` с тем же содержимым — повтор: он записывается в журнал как факт повторной доставки и больше ни на что не влияет. Тот же `event_id` с другим содержимым — конфликт: сообщение уходит в карантин, принятое не перезаписывается.

**Опоздания и время.** Время поступления фиксирует система. Событие помечается как `late`, если пришло позже порога (300 с), как `out_of_order`, если в его разделе уже есть более позднее событие, и как `clock_skew`, если его время в будущем больше чем на 60 с. Пороги — проектные предположения в `config/zero_defect.toml`.

**Пропуски.** Источник нумерует сообщения (`sequence_no`); разрывы в нумерации показываются как пропуски источника на экране линии.

**Состояние.** Единственное состояние, которое нельзя потерять, — журнал. Представления — кеш: они строятся из журнала при запуске и перестраиваются при изменении.

## 6. Хранение и защита

Подробно — в [security.md](security.md). Коротко:

- журнал в PostgreSQL (в тестах — ещё и SQLite тем же кодом); записи только дописываются, UPDATE, DELETE и TRUNCATE запрещены триггером в самой СУБД;
- запись журнала идёт под рекомендательной блокировкой PostgreSQL, поэтому несколько экземпляров сервиса на одной базе не разветвят цепочку;
- содержимое каждой записи зашифровано AES-256-GCM, открытый заголовок (вид, профиль, ключ, версия ключа, механизм) связан с шифротекстом как дополнительные данные AEAD;
- записи связаны цепочкой хешей, последняя запись каждого пакета подписана — гибридно Ed25519 + ML-DSA-65 в профиле по умолчанию;
- подписанная голова журнала (якорь) хранится отдельно от базы вместе с ключами и ловит отрезание хвоста;
- ключи — вне кода и репозитория, в каталоге `var/keys` с правами только для владельца;
- права ролей и аудит критических действий проходят через одну шину безопасности.

**Резервирование и восстановление.** Для резервной копии нужны согласованные дамп базы (`pg_dump`) и каталог ключей с якорем журнала; процедуру восстановления и проверку `/api/integrity` необходимо выполнить на целевом VPS до заявления об отказоустойчивости. В текущем `docker-compose.yml` нет ни автоматического резервирования, ни потоковой реплики PostgreSQL. Реплика и внешнее хранение якоря — проектный путь развития. Границы защиты: журнал защищён от незаметного изменения и чтения с диска, но сторона с одновременным доступом к базе и секретным ключам выходит за пределы этой модели угроз.

## 7. Масштабирование

**Вертикальное.** Число обработчиков приёма задаётся `ingest.workers`. Параметры, которые растут с нагрузкой: размер пакета приёма, окно связывания станков с операциями, объём кеша представлений.

**Целевой путь горизонтального масштабирования** разделяет стадии по их состоянию. Таблица описывает архитектурный план, а не готовую многопроцессную конфигурацию:

| стадия | состояние | как масштабируется |
|---|---|---|
| проверка и нормализация | нет | можно распараллеливать после подтверждения порядка и целостности результата |
| идемпотентность и порядок | транзакционный индекс `source_event_ids`; состояние порядка локально процессу | повтор исходного `event_id` защищён общей БД; владение разделами и межпроцессная синхронизация порядка ещё не реализованы |
| журнал | номер записи и хеш предыдущей | общий PostgreSQL сериализует запись в одну цепочку; разделение на несколько цепочек не реализовано |
| представления | производные, кешируются в памяти процесса | текущие представления обновляются внутри процесса; несколько копий приложения не получают автоматически изменения друг друга |

**Проверено измерением в одном процессе** ([scenarios.md](scenarios.md), `reports/metrics/load.json`): прогон с одним и четырьмя потоками, с перемешанным порядком и со сбоем центра и повторной доставкой дают одинаковый отпечаток показателей и статусов. Отдельные проверки общей дедупликации между двумя экземплярами системы добавлены в `tests/test_ingest.py`; они не доказывают синхронизацию их кешированных представлений и порядка. До реализации этой синхронизации на VPS следует запускать один процесс приложения.

**Узкие места, названные прямо.**
- Запись в журнал — одна точка на раздел: номер и хеш предыдущей записи берутся атомарно. Параллелить запись внутри раздела нельзя, не разорвав цепочку.
- Подпись ML-DSA стоит около 4,5 мс на операцию (профиль приёма). Поэтому подписывается последняя запись пакета, а не каждая; через цепочку она удостоверяет весь пакет. Это подняло пропускную способность приёма примерно в 20 раз.
- Обработчики в MVP — потоки одного процесса, и под GIL проверка сообщений почти не ускоряется: четыре обработчика дают тот же порядок скорости, что и один. Масштабирование на процессы или узлы потребует распределить владение разделами и синхронизировать проекции, как намечено для будущего Kafka-потребителя.
- Представления пересобираются целиком. На тысячах изделий это доли секунды; на миллионах нужна инкрементальная проекция в PostgreSQL.

## 8. Развитие: как добавить OpenTelemetry и Kafka

Постановка спрашивает, как переданная заказчику система дополняется экспортом метрик через OpenTelemetry или брокером сообщений, например Kafka. Ответ — какие модули, интерфейсы, настройки и проверки это затрагивает.

### OpenTelemetry

- **Интерфейс:** порт `Telemetry` в `observability.py` — `count`, `observe`, `snapshot`. Ядро уже пишет в него счётчики сообщений по статусам и время обработки пакета.
- **Модуль:** новая реализация `OtelTelemetry` рядом с `InMemoryTelemetry`, которая переводит `count` в `Counter.add`, а `observe` — в `Histogram.record` SDK OpenTelemetry. Ядро, эндпоинты и правила не меняются.
- **Настройки, которые ещё нужно добавить:** секция `[telemetry]` в `config/zero_defect.toml` — `exporter = "otlp"`, `endpoint`, `service_name`; сейчас `QualitySystem` создаёт `InMemoryTelemetry` напрямую, поэтому выбор реализации потребует изменения сборки зависимостей.
- **Проверки:** тест с `InMemoryMetricReader` из SDK, который проверяет, что после приёма пакета появились `ingest.messages{status=accepted}` и `ingest.batch_seconds`; в CI — тот же тест.

### Kafka

- **Интерфейс:** приём уже принимает пакет `Delivery` (сообщение и момент поступления) — это и есть граница транспорта. HTTP-эндпоинт `/api/events` — один из транспортов.
- **Модуль:** проектируемый `ingest/kafka_source.py` — потребитель группы, который читает пакет, вызывает `QualitySystem.ingest_deliveries` и подтверждает смещение только после записи в журнал. Ключ сообщения Kafka — тот же ключ раздела (`item_id`), поэтому порядок в пределах изделия сохраняется разделом Kafka. До запуска нескольких потребителей нужны проверенная межпроцессная дедупликация по `event_id`, согласование проекций и отдельный прогон восстановления после сбоя.
- **Исходящая сторона:** исходящая очередь (`integration/hub.py`) пишется в тот же журнал и уже отделена от отправки; публикация итогов в тему Kafka — ещё один адаптер порта `ExternalSystem`.
- **Настройки:** `[transport] kind = "kafka"`, `bootstrap_servers`, `topic`, `group_id`, размер пакета, политика подтверждения.
- **Проверки:** интеграционный тест на Kafka в контейнере, повторяющий `tests/test_scaling.py`: поток с повторами и перезапуском потребителя даёт тот же отпечаток, что и прямой приём; контрактная проверка сообщений темы той же JSON Schema.

### Predictive и MobileOps — архитектура без реализации

- **Predictive** подписывается на события ядра и читает историю через `state()`: признаки — отклонения оборудования в окне операции, повторные обработки, длительности по сопоставимым работам. Его выход — ещё один источник событий со своим типом (гипотеза о риске), который проходит тот же приём и никогда не меняет статус карточки сам. Реализации нет, поэтому о точности прогноза проект ничего не утверждает.
- **MobileOps** — беспроводное взаимодействие с роботами и мобильными терминалами: те же edge-агенты с буфером и подписью пакета, но с прерывистой связью как штатным режимом, а не аварией. Буфер агента и идемпотентность приёма для этого уже есть; нужен транспорт с подтверждением (MQTT QoS 1 или Kafka) и управление ключами устройств.

## 9. Расширяемость

- **Новый адаптер внешней системы** подключается строкой в `[integration] enabled` и секцией с `factory = "пакет.модуль:функция"`: реестр импортирует модуль при запуске, ни ядро, ни реестр править не нужно. Это проверено тестом `test_third_party_adapter_plugs_in_through_config`.
- **Новая версия контракта** — новый файл схемы и перегенерация; нормализация приводит её к той же внутренней модели, правила разбора не трогаются. CI проверяет совместимость соседних версий.
- **Новый криптографический профиль** — ещё одна запись в `PROFILES`; формат записи уже несёт идентификатор профиля.
- **Замена хранилища** уже проверена: весь доступ к базе идёт через таблицы SQLAlchemy в `storage/database.py`, а то, что зависит от диалекта — защита журнала, блокировка писателя, вставка без повторов, — собрано там же. Тесты журнала и проверочные ситуации идут на PostgreSQL и SQLite одним кодом.

## 10. Развёртывание

Полный состав — три контейнера (`docker compose up`): сервис, PostgreSQL и эмулятор внешней системы. База — в своём томе, ключи и якорь журнала — в отдельном: копия базы без ключей бесполезна. Ключи создаются при первом запуске внутри тома и в образ не попадают. Внешних обращений нет: интерфейс, шрифты и скрипты отдаются самим сервисом.

Для разработки предусмотрен отдельный [временный стенд Render](render.md): один бесплатный веб-сервис с условной базой SQLite и ключами в одном временном файловом пространстве. После засыпания или перезапуска история создаётся заново; двусторонний обмен с внешним MES-эмулятором на этом стенде отключён. Это не конфигурация итогового развёртывания. Настройка VPS описана в [deploy-vps.md](deploy-vps.md).

## 11. Линии, эмулятор и основной экран

**Линия — граф.** Узел — этап: операция (участок, оборудование, операция техпроцесса) или контроль (контрольная точка); ребро — порядок процесса; узел с несколькими входами — сборка. Конфигурация линии хранится в базе (`lines`), каждое её изменение — новая версия и критическое действие в журнале. Событие относится к этапу по участку и операции техпроцесса или по контрольной точке, поэтому одни и те же представления работают для настоящей линии, для проверочных ситуаций и для эмулятора.

**Справочник оборудования** (`lines/equipment.py`, таблица `equipment`). Тип станка задаёт обработку, которую он выполняет, виды дефектов, которые на нём возникают, и параметры режима, которые он пишет в MachineLogs. Станок — экземпляр типа со своим кодом, инвентарным номером, состоянием и допусками параметров. Тип станка и виды дефектов — шаблоны, их ведёт администратор (`lines/registry.py`, таблица `catalog`; встроенные значения — начальное наполнение). Конкретный станок по типу заводит технолог (право `equipment_manage`); руководитель в редакторе ставит операцию только на станок из справочника, и сервер при сохранении линии проверяет, что станок зарегистрирован и не списан, обработка — из тех, что выполняет его тип, а дефекты — из тех, что на нём возникают. Допуски демонстрационных станков условные. Коды участка, операции и контрольной точки при правке существующей линии сохраняются: по ним к этапу привязана история.

**Эмулятор конвейера** (`lines/emulator.py`) ведёт изделия по графу и порождает события так, как их прислали бы терминалы участков, журналы станков и анализаторы: с вероятностью дефекта этапа, доработкой устранимых дефектов, изоляцией изделия при обнаружении несоответствия, редкими отклонениями станка и недостоверными наблюдениями. Он работает в трёх режимах: история (сотни изделий за прошедшие смены с решениями контролёров — так наполняется демонстрационная база), живой (новое изделие раз в такт с ускорением) и загруженный поток ([flows.md](flows.md)). Эмулятор пишет только через приём — проверка, журнал и разбор те же, что для событий настоящей линии.

**Основной экран** — граф линии в духе SCADA: изделия движутся по этапам, у этапа видны прошедшие изделия, обнаруженные здесь и ждущие решения несоответствия (красная метка) и возникшие здесь по оценке системы (оранжевая). Под графом — статистика этапов с фильтрами по типу изделия, смене и периоду; справа — детали выбранного: этап, маршрут изделия A → B → C, карточка несоответствия, таблица изделий с фильтрами по столбцам, экономика, редактор линии, загрузка потока. Слева — инструкция и панель роли: у каждой роли первым показано то, с чем она работает. Экран один, вкладок нет.

**Экономика линии** (`lines/views.py`) — параметры, которые задаёт главная роль (стоимость годного, доработки, потерь, часа участка, длительность смены), умноженные на измеренные величины: число годных и несоответствующих изделий, доработок, часы на участках, медианы длительностей. Отсюда потери от брака и их доля в выпуске, затраты на годное изделие, узкое место и пропускная способность за смену, а также распределение потерь по этапам, где дефекты возникли. Числа без параметров не появляются: на демонстрационных линиях параметры условные и помечены так в интерфейсе.

## 12. Экран линии, шкала времени и производительность

**Структура экрана.** Обзор производства (`/api/plant`) — первый экран. Экран линии — единственное место работы: граф в центре, панель роли слева, шкала времени снизу; таблица этапов выпадает сверху по кнопке, подробности открываются во вкладках под линией по нажатию на станок, метку, изделие или запись очереди. Эмуляция вынесена в отдельный пульт (`/emulator`): система не отличает его от настоящих источников, и в интерфейсе самой системы кнопок эмуляции нет.

**Проблемы линии** (`lines/views.py: line_problems`). Проблема — это несоответствие (решается закрытием после устранения или отклонением сигнала) или наблюдение «оценка невозможна» (решается повторным достоверным контролем в той же контрольной точке или допуском по ручному контролю). «Оценка невозможна» — проблема, но не брак: постановка не разрешает считать плохой снимок ни годностью, ни браком, поэтому разбор этапа по ней не выполняется. Одна проблема — одна запись в месте обнаружения. Очередь контролёра всегда о настоящем. Над этапом один красный круг — число проблем, действующих на момент конца промежутка. Решённость берётся на настоящее время: проблема, решённая позже конца промежутка, в прошлом тоже считается решённой. Нажатие на круг открывает список, в конце которого серым — решённые. Счётчики изделий под этапом — о самом этапе: проблема обнаружена здесь, оценка невозможна здесь, изделие в работе или прошло этап без проблем. Поэтому красный и жёлтый счётчики сходятся с кругом, а сумма — с числом изделий за промежуток. «На рассмотрении» и «несоответствие» различаются в карточке и в статусе изделия, а на графе это одна «проблема на этапе».

**Проблемы оборудования** (`lines/views.py: machine_problems`). Сбой станка — эпизод от выхода из нормального режима до возврата в работу; несколько сообщений о сбое подряд — один эпизод. Технолог работает именно с ними: его очередь, круги над этапами и дорожка шкалы — сбои станков. Подтверждённые несоответствия остаются у него отдельным списком, потому что причину по ним устанавливает технолог (ситуация 07 постановки).

**Решения по «оценка невозможна».** Мастер участка и контролёр назначают повторный контроль или допускают изделие по ручному контролю (`POST /api/unassessable/{id}/decisions`, право `decide_unassessable`). По несоответствиям мастер решает так же, как контролёр (право `decide`), а автор и роль каждого решения остаются в журнале. Решение — такая же отдельная запись журнала, как решение по несоответствию, с номером проблемы `NA-<event_id>`. Проблему снимает повторный достоверный контроль в той же контрольной точке или допуск по ручному контролю. Достоверный контроль на более позднем этапе её не снимает: он видит изделие уже после следующих операций. Пока проблема не снята, изделие не признаётся годным, а живая эмуляция держит его у контрольной точки до решения. Автоматически плохой снимок годностью не становится: годность здесь всегда решение человека.

**Решение продолжает изделие в эмуляции** (`lines/follow_up.py`). Изделие с обнаруженным дефектом эмулятор изолирует: дальше по линии оно не идёт. Записанное решение ядро рассылает слушателям, и эмулятор отвечает событиями, как участок. Подтверждение дефекта операции — доработка на ней, повторный контроль в той же точке и путь дальше, со сборкой, если остальные компоненты комплекта уже ждут. Отклонение сигнала или закрытие — путь дальше без доработки. Запрос повторного контроля — ещё один снимок: признак подтвердится или нет. Входной дефект на линии не дорабатывается: изделие ждёт допуска или списания. Решения из истории демонстрационной базы изделий не двигают: слушатель берёт только решения последних двух минут.

**Шкала времени — промежуток.** Два ползунка задают начало и конец, промежуток целиком сдвигается перетаскиванием. Граф показывает линию на конец промежутка; числа изделий под этапами и таблица этапов считаются внутри него, в таблице рядом — на текущий момент. Длина по умолчанию задаётся в конфигурации (`[interface] default_window`: календарные сутки или смена, `shift_hours`). Отметки шкалы связаны только с проблемами и окрашены тремя цветами: красный — проблема, жёлтый — оценка невозможна, зелёный — решено. Дорожка изделий — обнаружение и решение, дорожка станков — сбой и возврат в работу. У выбранной проблемы обе отметки соединены линией; решённые можно скрыть.

**Роли и администрирование.** Роли и их права лежат в справочнике (`security/roles.py`); администратор заводит новые роли с одним из готовых экранов и пользователей. Экран привязан к роли: у каждой роли свой базовый экран (у администратора — «Администрирование», у остальных — обзор производства) и своя память о последнем открытом. Смена роли в «Смотреть как» открывает её базовый экран.

**Панели и окна.** Таблица этапов раскрывается над графом в его ширину и сдвигает экран вниз. Подробности выводятся во вкладках под линией: «Изделие и проблема», «Этап», «Изделия линии», «Экономика». Изделие и проблема — одна вкладка из двух половин: слева изделие, справа проблема; выбор проблемы сразу открывает её изделие, выбор изделия справа показывает его проблемы. Выплывающие панели закрываются плавно, в том числе нажатием вне их. Пульт эмулятора открывается в том же окне. Панель администратора свёрнута в ☰ и при открытии сдвигает поле линии. Экономика открывается в одном месте — кнопкой в шапке линии. Длинные подписи в блоках графа и редактора не обрезаются, а бегут строкой.

**Оценка показателей цветом.** Показатели этапа и ячейки таблицы этапов окрашены по четырём уровням: хорошо, терпимо, плохо, очень плохо. Пороги — доли: медиана длительности к норме, доработки и отклонения станка на выполнение, возникшие дефекты на изделие, проверки с признаками и без оценки; порог каждой плитки виден в подсказке. Пороги условные: на предприятии их задают технолог и ОТК.

**Сбои станка у технолога.** У операции в панели деталей — станок: полоса последних состояний (зелёное — работа, красное — режим вне допуска) и график каждого параметра режима с полосой допуска из справочника; точки вне допуска красные. В панели технолога такая же полоса есть у каждого станка линии вместе с числом сбоев.

**Состояние на момент времени.** `QualitySystem.state_at(t)` строит представления только из событий, случившихся до `t`, и решений, принятых до `t`; все эндпоинты линии принимают параметр `at`. На этом держатся шкала времени, воспроизведение истории и откат к моменту отказа из очереди. Решение, принятое при просмотре прошлого, записывается текущим временем, и карточка об этом предупреждает: иначе переход из очереди в момент обнаружения мешал бы контролёру работать.

**Откуда брались лаги и что изменено.** Замер на базе из 1704 изделий и 13 867 событий показал две причины.
- Связывание состояний станка с операциями было квадратичным: каждое выполнение сравнивалось с каждым событием своего станка — 2,3 млн сравнений и 73 % времени пересборки истории. Теперь окно операции находится двоичным поиском по отсортированным событиям станка. Пересборка всех представлений: 0,84 с → 0,135 с.
- Пока идёт эмуляция, новые события приходят каждую секунду, и каждый опрос интерфейса запускал полную пересборку под общей блокировкой — приём событий в это время ждал. Теперь интерфейс читает снимок не старше секунды (`snapshot`), пересборка идёт вне блокировки приёма, а решения людей по-прежнему идут по самому свежему состоянию. Интерфейс не отправляет следующий опрос, пока не вернулся предыдущий, и не опрашивает скрытую вкладку.
- Загрузка демонстрационной базы из 900 комплектов с решениями: 108,8 с → 30,5 с.

Второй замер — на рабочей базе в 43 тыс. записей после нескольких часов эмуляции: полная пересборка занимала 1,4 с, переход к проблеме в прошлом — 2,6 с до карточки.
- Разбор причины для каждой карточки проходил по всем наблюдениям и выполнениям истории, а статус каждого изделия — по всем карточкам. Теперь и то и другое берётся по изделию. Средние длительности считаются `fmean` вместо точных дробей `mean`. Пересборка на 43 тыс. событий: 1,4 с → 0,3–0,5 с.
- `snapshot` больше не ждёт пересборку: отдаётся последний готовый снимок, свежий строится в фоне не чаще раза в секунду. Решения людей и ответ на них по-прежнему читают `state()`.
- Состояние на прошедший момент строится один раз, даже если его одновременно просят несколько запросов, и сбрасывается только событиями и решениями не позже этого момента: эмуляция пишет «сейчас», и прошлое от неё не меняется.
- Живая эмуляция запускает новые изделия, только пока экран линии кто-то смотрит (последний опрос не старше 5 минут). Без этого развёрнутый сервис без зрителей набирал около 11 тыс. записей в час, и за сутки память и время пересборки выросли бы в разы. Кэш состояний на прошедшие моменты держит 4 снимка вместо 12: на 22 тыс. событий дюжина снимков добавляла около 80 МБ.
- Интерфейс не перерисовывает очередь и шкалу, если данные не изменились, открывает карточку проблемы параллельно с переходом во времени и показывает её до того, как догрузится маршрут изделия. Переход к проблеме: 2,6 с → 0,7 с до карточки.

Замеры сняты скриптом профилирования на одной машине и в репозиторий отчётом не выложены; порядок проверяется тестом `test_scaling.py` и ручным прогоном из этого раздела.
