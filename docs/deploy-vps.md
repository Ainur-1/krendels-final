# Финальный демонстрационный стенд на VPS

Основание: постановка, с. 4 («Защита»), с. 7 (п. 3.4 «Хранение и базовая защита») и с. 12 (п. 7.1 «Образ результата»); критерии, с. 3, технические № 1 «Работоспособность и воспроизводимость кода», № 3 «Информационная безопасность и аудит», № 5 «Полнота и качество документации». Пайплайн и стенд дают проверяемый запуск MVP, но сами по себе не доказывают полноту сценариев или промышленную защиту.

Адрес стенда для жюри: `http://135.106.196.206:8000/`. Это открытый демонстрационный контур **только с синтетическими данными**. До первой успешной выкладки ссылка может не отвечать. Публичный HTTP не шифрует трафик до браузера; демонстрационные пароли и выбор роли нельзя применять для реальных данных. Компоненты на одном VPS общаются по внутренней сети Docker Compose по HTTP; при разнесении по узлам нужен отдельно настроенный TLS. Ограничения защиты описаны в [security.md](security.md).

## Состав и текущее состояние

На VPS `135.106.196.206` 26 сентября 2026 проверены Ubuntu 26.04, 3,8 ГиБ памяти, диск 4,9 ГиБ, доступ по SSH. При осмотре старых контейнеров, Docker и сервисов на порту 8000 не было. Docker Engine и Compose установлены из официального репозитория Docker. Каталог `/opt/krendels-final` содержит файл `.env` с правами `0600`; пароль базы создан случайно на самом сервере и не хранится в Git или CI. Публичен только порт приложения 8000; PostgreSQL и MES-эмулятор в [`deploy/compose.vps.yml`](../deploy/compose.vps.yml) не публикуют порты. Тома `krendels-final-db` и `krendels-final-keys` принадлежат только финальному проекту.

Текущее развёртывание и проверенный SHA следует определять командами ниже, а не по этому описанию.

## Автоматическая публикация из GitHub

Единый workflow [`.github/workflows/pipeline.yml`](../.github/workflows/pipeline.yml) запускается на `push` в `main` и для pull request. Задача `backend` проверяет стиль, тесты, совместимость контрактов, OpenAPI и проверочные сценарии. Задача `image` начинается только после успешного `backend` и собирает Docker-образ с меткой SHA. Только для `push` в `main` она передаёт **этот же образ** по SSH на VPS, обновляет Compose и ждёт здорового приложения. В конце runner делает запрос к публичному `/api/health`. Ошибка любого шага делает workflow красным; pull request не публикуется.

Для доступа нужен секрет репозитория GitHub Actions `DEPLOY_SSH_KEY`: приватный ключ отдельной пары без пароля. Публичная половина находится в `/root/.ssh/authorized_keys` на VPS с ограничениями `restrict` и `command="/opt/krendels-final/ci-ssh.sh"`. Этот ключ выполняет только две операции: приём образа и запуск заранее установленного Compose с указанным SHA. Произвольный shell, SFTP и перенаправление портов запрещены. Ключ сервера закреплён в [`deploy/known_hosts`](../deploy/known_hosts); workflow отвергает неизвестный или изменившийся ключ. Приватный ключ не включают в репозиторий, контейнерный образ, отчёты или логи. Для публикации используется передача образа `docker save` по SSH, поэтому пароль контейнерного реестра не нужен.

Начальная настройка чистого сервера воспроизводится [`deploy/bootstrap-vps.sh`](../deploy/bootstrap-vps.sh), запуск образа — [`deploy/activate.sh`](../deploy/activate.sh). Ограничение CI-ключа реализует [`deploy/ci-ssh.sh`](../deploy/ci-ssh.sh). Эти файлы устанавливает на VPS администратор через обычный SSH; CI не может их менять. Не запускать bootstrap повторно для смены пароля: существующий `.env` он сохраняет. Ручной запуск требует предварительно передать на VPS образ с тегом SHA; затем выполнить `ZD_IMAGE=zero-defect:<SHA> bash /opt/krendels-final/activate.sh`. Скрипт сверяет метку SHA в работающем контейнере и при ошибке пытается вернуть предыдущий образ.

## Проверка релиза

На сервере:

```bash
cat /opt/krendels-final/current-image
docker compose --env-file /opt/krendels-final/.env -f /opt/krendels-final/compose.vps.yml ps
docker inspect -f '{{index .Config.Labels "org.opencontainers.image.revision"}}' krendels-final-app-1
curl -fsS http://127.0.0.1:8000/api/health
```

С отдельного подключения открыть `http://135.106.196.206:8000/` и `/api/health`, затем пройти вход условной ролью, историю изделия, карточку несоответствия и двусторонний обмен с эмулятором. Проверить, что SHA метки контейнера равен нужному успешному коммиту `main`. Здоровый `/api/health` сам по себе не доказывает весь сценарий.

## Данные, резервирование и восстановление

База и ключи лежат в разных Docker-томах. Их резервные копии нужно делать **согласованно**, хранить за пределами VPS и проверять восстановление на отдельном стенде. Копия только базы без тома ключей не позволяет прочитать зашифрованную историю; потеря обоих томов не устраняется повторным деплоем образа. До настроенной и проверенной процедуры резервирования не обещаем восстановление после потери VPS. На открытом стенде остаются только синтетические данные.

## Переход в GitVerse

Этот workflow предназначен для разработки в GitHub. Перед переносом зафиксировать успешно развёрнутый SHA `main`. После переноса сверить этот SHA и обязательные файлы в GitVerse, затем проверить фактический запуск его CI. Не копировать workflow в `.gitverse/workflows/` без проверки текущей документации GitVerse и отсутствия дублирующих запусков: платформа может обнаруживать `.github/workflows/`. Временный Render-стенд с SQLite описан отдельно в [render.md](render.md) и не доказывает работу VPS с PostgreSQL и эмулятором.
