# Загружаемый поток

Поток — это JSON-файл, по которому система проигрывает работу линии на экране: этапы процесса с длительностями и вероятностями дефекта, сколько изделий пропустить, за сколько секунд показать весь прогон и в какие изделия и этапы внести дефект принудительно. Ускорение считается само: весь процесс укладывается в заданное время показа.

Основной путь — **форма в пульте эмулятора** (`/emulator`): выбирается существующая линия, вбиваются число изделий, время показа, вероятности дефекта по этапам и принудительные дефекты «изделие № → этап» (`POST /api/lines/{id}/runs`). Файл `zd-flow/1` нужен, когда контракт пришёл документом целиком — с описанием линии: он вставляется в пульте в поле «Импорт JSON» или отправляется в `POST /api/flows`. Линия из файла создаётся или обновляется новой версией, и прогон сразу идёт на графе. Пример на минуту показа — [data/flows/bracket_minute.json](../data/flows/bracket_minute.json); он же открывается кнопкой «Взять пример».

## Формат `zd-flow/1`

```json
{
  "format": "zd-flow/1",
  "line": {
    "line_id": "DEMO",
    "title": "Демонстрация · кронштейн",
    "product_type_id": "BRACKET-D1",
    "takt_min": 6,
    "steps": [
      {"title": "Входной контроль листа", "kind": "inspection", "duration_min": 2, "defect_rate_pct": 2, "defect_types": ["LAMINATION"]},
      {"title": "Лазерная резка", "kind": "operation", "duration_min": 7, "defect_rate_pct": 3, "defect_types": ["BURR"], "rework_types": ["BURR"], "equipment_id": "LASER-D1", "operators": ["OP-D1"]},
      {"title": "Финальный контроль ОТК", "kind": "inspection", "duration_min": 3}
    ],
    "economics": {"item_value_rub": 24000, "rework_cost_rub": 1200, "scrap_cost_rub": 17000, "hour_cost_rub": 3100, "shift_hours": 12}
  },
  "run": {
    "items": 24,
    "duration_s": 60,
    "seed": 7,
    "defects": [{"item": 5, "stage": 2, "kind": "defect"}]
  }
}
```

| поле | смысл |
|---|---|
| `line.line_id` | код линии: латиница, цифры, `-` и `_` |
| `line.product_type_id` | тип изделия, которое проходит линию |
| `line.takt_min` | такт: через сколько минут запускается следующее изделие |
| `steps[].kind` | `operation` — операция, `inspection` — контроль |
| `steps[].duration_min` | длительность этапа в минутах процесса |
| `steps[].defect_rate_pct` | вероятность, что изделие получит дефект на операции или придёт с ним на входной контроль |
| `steps[].defect_types` | коды дефектов, которые возникают на этапе |
| `steps[].rework_types` | дефекты, которые устраняются повторной операцией, а не браком |
| `steps[].checkpoint_kind` | необязательно: `incoming`, `after_operation`, `final`; по умолчанию первый контроль — входной, последний — финальный |
| `line.economics` | параметры экономики линии: стоимость годного, доработки, потерь на браке, часа участка, длительность смены |
| `run.items` | сколько изделий пропустить, до 200 |
| `run.duration_s` | за сколько секунд показать весь прогон, 10–900 |
| `run.seed` | зерно случайности: тот же файл — тот же прогон |
| `run.defects` | принудительные дефекты: изделие (с 1), этап (с 1), `defect` или `deviation` — отклонение станка на операции |

Файл проверяется целиком до запуска: дефект на несуществующем этапе или у несуществующего изделия, цикл в графе, операция без длительности — ответ 422 с причиной, прогон не начинается.

## Что происходит при прогоне

Эмулятор планирует все изделия сразу и отдаёт события в систему в темпе показа — через тот же приём, журнал и разбор, что и события настоящей линии. Изделие с обнаруженным несоответствием изолируется и дальше по линии не идёт; дефект из `rework_types` отправляется на доработку и повторный контроль. Время событий сжато ускорением, а длительности операций источник сообщает в масштабе процесса — поэтому таблица этапов показывает минуты техпроцесса, а не секунды показа.

Все параметры потока — условные данные для показа, а не измерения реальной линии.
