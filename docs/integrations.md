# Интеграции

В MVP целиком реализован один двусторонний обмен — с эмулятором внешней системы уровня MES/ERP: получение заданий и справочников и отправка итогов контроля с подтверждением или ошибкой. Для 1С, Галактики ERP, MES по ISA-95 и КОМПАС-3D есть адаптеры с преобразованием форматов, примеры сообщений и тесты на них; сетевое подключение к настоящим системам требует их стендов.

## 1. Принципы

- **Внутренняя модель и форматы внешних систем различимы.** Ядро видит `WorkOrder`, `ReferenceData`, `QualityResult` и `Ack` (`integration/model.py`). Перевод из формата 1С, Галактики или MES и обратно выполняется в адаптере на границе. Изменение формата внешней системы меняет один адаптер, а не правила разбора.
- **Один порт на все системы.** Адаптер реализует три операции: `fetch_work_orders`, `fetch_reference`, `send_result`.
- **Входящее направление — через тот же приём.** Задание превращается в события `item_registered` и проходит ту же проверку, идемпотентность и журнал, что и события линии. Изделие, уже сопоставленное с системой, повторно не регистрируется.
- **Исходящее направление — через очередь.** Итог по изделию кладётся в исходящую очередь и только потом отправляется. Временная ошибка (5xx, обрыв связи) оставляет сообщение в очереди с паузой, растущей вдвое от 5 с до часа; ошибка содержания (4xx) уводит его в недоставленные с причиной — повтор её не исправит. Каждая попытка пишется в журнал записью `integration_exchange`.
- **Идемпотентность исходящих сообщений.** Идентификатор итога вычисляется из изделия, его статуса и карточек, поэтому повторная синхронизация того же итога — тот же идентификатор, и принимающая сторона отбрасывает повтор.
- **Сопоставление идентификаторов** хранится в таблице `id_map` (система, сущность, внешний идентификатор, внутренний) и видно на экране «Интеграции».

## 2. Кто источник достоверных сведений

| сведения | источник истины | направление |
|---|---|---|
| номенклатура, типы изделий | 1С / Галактика ERP | → к нам |
| производственные задания и серийные номера | ERP через MES | → к нам |
| состав сборки | КОМПАС-3D (через САПР или файл) | → к нам |
| события операций | MES / терминалы участков | → к нам |
| результаты контроля, несоответствия, решения, причины | **наша система** | → в ERP и MES |

## 3. Эмулятор (реализован)

`zero_defect.integration.emulator` — отдельный процесс со своим форматом, намеренно не похожим на внутренний: заказ — `orderNo`, изделие — `serial`, итог — `verdict` `OK/NOK/HOLD`.

| запрос | смысл | ответы |
|---|---|---|
| `GET /api/v1/orders` | задания с серийными номерами и составом | 200; 503 при включённом сбое |
| `GET /api/v1/catalog` | справочники изделий, кодов дефектов, участков | 200 |
| `POST /api/v1/quality-reports` | итог контроля | 202 `accepted` со ссылкой `QR-…`; 200 `duplicate` для повторного `msgId`; 422 `unknown_serial` или `bad_verdict` |
| `POST /admin/faults` | следующие N запросов отвечают заданным кодом | для демонстрации сбоя |

Проверено тестами (`tests/test_integration.py`): задание регистрирует 6 изделий; после изготовления узла итог уходит и принимается; повторная синхронизация ничего не отправляет повторно; при 503 сообщение остаётся в очереди и уходит со второй попытки; неизвестный серийный номер уходит в недоставленные с кодом `unknown_serial`.

## 4. 1С:Предприятие — REST-интерфейс OData

- **Транспорт:** стандартный интерфейс OData платформы 8.3.5+, `/odata/standard.odata/…?$format=json`, базовая авторизация служебной учётной записи.
- **Вход:** `Catalog_Номенклатура` (Ref_Key, Code, Description) → типы изделий; `Document_ЗаказНаПроизводство` с табличной частью «Продукция» → задания.
- **Выход:** документ `Document_КонтрольКачества` с результатом «Годно / Брак / НаПроверке», серийным номером, ссылкой на номенклатуру и списком несоответствий.
- **Идентификаторы:** в 1С — GUID `Ref_Key`; внутренний код типа — реквизит `Code`. Итог уходит со ссылкой `Номенклатура_Key` из сопоставления.
- **Ошибки:** номенклатура из заказа без сопоставления — ошибка содержания, заказ не принимается, причина названа; 5xx — повтор по очереди.
- **Проектное предположение:** имена объектов конфигурации заданы в `OBJECTS` адаптера и в конкретной конфигурации могут отличаться.
- Примеры: [onec_nomenclature.json](../contracts/examples/onec_nomenclature.json), [onec_orders.json](../contracts/examples/onec_orders.json). Адаптер: `integration/adapters/onec.py`.

## 5. Галактика ERP — файловый XML-обмен

- **Транспорт:** каталоги обмена `inbox/` (от ERP) и `outbox/` (к ERP). Не требует сетевого доступа из ERP к нашей системе, что удобно в закрытом контуре.
- **Вход:** `nomenclature.xml`, `orders.xml` с единицами изделия, их происхождением и принадлежностью к сборке.
- **Выход:** файл `<messageId>.xml` с вердиктом `ACCEPT / REJECT / HOLD` и списком несоответствий. Запись атомарная: сначала `.part`, затем переименование — ERP никогда не увидит недописанный файл. Повторная отправка того же итога не создаёт второго файла.
- **Ошибки:** повреждённый XML — ошибка содержания с текстом разбора.
- **Проектное предположение:** структура XML согласуется с интегратором ERP.
- Примеры: [galaktika_nomenclature.xml](../contracts/examples/galaktika_nomenclature.xml), [galaktika_orders.xml](../contracts/examples/galaktika_orders.xml). Адаптер: `integration/adapters/galaktika.py`.

## 6. MES — модель ISA-95 (IEC 62264)

- **Вход:** `OperationsSchedule` с запросами на сегменты и партиями материала (`MaterialLotID`) → задания; `MaterialUse = Consumed` означает покупной компонент.
- **Выход:** `OperationsPerformance` с результатом испытаний по каждому серийному номеру и решением `Pass / Fail / Pending`.
- **Без повторного ручного ввода:** задания и серийные номера приходят из MES, итоги уходят в MES — оператор ОТК ничего не переносит руками.
- **Оговорка:** это JSON по образцу B2MML, а не полное соответствие схемам XSD; конкретная MES поддерживает подмножество, которое согласуется при подключении. События операций от MES приходят по нашему контракту событий.
- Пример: [isa95_operations_schedule.json](../contracts/examples/isa95_operations_schedule.json). Адаптер: `integration/adapters/mes_isa95.py`.

## 7. КОМПАС-3D — состав сборки

- **MVP:** файл с условной структурой сборки — идентификатор, версия, компоненты с количеством и происхождением, связи. Геометрии нет, и это указано явно: `"geometry": null`; файл без этого поля отклоняется.
- **Прямое подключение:** через COM API КОМПАС (API7) — `KompasComSource` открывает документ сборки и читает дерево `TopPart → Parts`, приводя результат к той же `AssemblyStructure`. Работает только под Windows с установленным КОМПАС; на другой системе объясняет это ошибкой, а не падает. Имена свойств API требуют сверки с SDK версии, установленной на предприятии — этот путь без КОМПАС не проверен.
- Пример: [kompas_assembly.json](../contracts/examples/kompas_assembly.json). Адаптер: `integration/adapters/kompas.py`.

## 8. Как подключить новую систему

1. Написать модуль с классом или функцией, принимающей `AdapterSettings` и реализующей три операции порта.
2. Добавить в `config/zero_defect.toml`:
   ```toml
   [integration]
   enabled = ["mes_emulator", "my_system"]

   [integration.my_system]
   factory = "my_package.adapter:MySystemAdapter"
   base_url = "http://my-system.local"
   ```
3. Перезапустить сервис. Ядро, реестр и правила не меняются — это проверено тестом `test_third_party_adapter_plugs_in_through_config`.
