# Ожидаемые результаты

## 1. Что получает предприятие

Постановка формулирует цель системы так: сокращать время обнаружения и разбора несоответствий, сохранять основания для выводов и помогать предупреждать повторный брак. Ниже — чем именно решение этому служит. Количественные эффекты для конкретного предприятия здесь не приводятся: реальных данных нет, а числа без измерения мы не пишем. Как их измерить на пилоте — в разделе 3.

| кто | что меняется |
|---|---|
| контролёр качества | вместо разрозненных записей — карточка, где рядом исходные сообщения анализатора как пришли, разбор с основаниями и альтернативами и история решений; решение принимается кнопкой с обязательным обоснованием и больше не может быть незаметно изменено |
| мастер участка | состояние линии: что в работе, какие операции не завершены, какие проверки ждут решения, от каких источников не дошли сообщения |
| технолог | связь дефектов с операциями, режимами оборудования и действиями; подтверждённые ошибки по сопоставимым работам; выгрузка истории в OCEL 2.0 для анализа процессов своими инструментами |
| руководитель производства | показатели качества, длительности, повторной обработки и повторяемости, где входной брак, проблемы оборудования, ошибки операторов и гипотезы разведены |
| администратор | проверка целостности журнала одной кнопкой, смена ключей и профилей без перешифрования истории, журнал критических действий |
| ИТ предприятия | задания и итоги ходят между MES/ERP и системой без повторного ручного ввода; новый источник или внешняя система подключается конфигурацией |

Главное качественное отличие — **система не выносит приговоров, которых не может обосновать.** Входной брак не приписывается оператору следующей операции, «признаков нет» при плохом снимке не превращается в «годно», а ошибка оператора появляется только как решение человека. Это то, что делает выводы системы пригодными для разбора с участием людей, чьи действия разбираются.

## 3. Как измерить эффект на пилоте

Числа эффекта появятся только из данных пилота. Система уже считает то, что для этого нужно, — сравнение «до» и «после» требует лишь зафиксировать исходный уровень до запуска.

| эффект | показатель | где он в системе |
|---|---|---|
| раньше обнаруживать | задержка обнаружения: от завершения операции-источника до первого сигнала | `extra.detection_delay_s` |
| быстрее разбирать | время от первого сигнала до решения контролёра | журнал решений карточки |
| меньше неустановленных причин | доля подтверждённых несоответствий с установленной причиной | `causes.established` / `not_established` |
| меньше повторного брака | повторяющиеся сочетания «дефект — операция — оборудование» после подтверждённой причины | `defects.by_type`, `comparable_work` |
| меньше ложных срабатываний | доля отклонённых контролёром сигналов по версиям анализатора | `defects.rejected`, `analyzer_version` |
| меньше доработок | повторные обработки и прохождение с первого раза | `operations.rework_runs`, `extra.first_pass_yield` |

## 4. Ограничения

- Данные условные; пороги (опоздание 300 с, расхождение часов 60 с, минимальная уверенность 0,6, окно связывания станка 300 с) — проектные предположения из `config/zero_defect.toml`.
- Разбор этапа опирается на то, что контрольная точка видит изделие целиком; если точка видит только часть поверхности, это нужно отразить в справочнике точек — в MVP такого справочника нет.
- Обработчики приёма — потоки одного процесса; горизонтальное масштабирование описано, но не реализовано.
- Адаптеры 1С, Галактики, MES и прямое подключение к КОМПАС проверены на примерах сообщений, а не на живых системах.
- ГОСТ-профиль криптографии описан, но не реализован.
