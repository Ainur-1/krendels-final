# Защита информации

Постановка разводит три задачи — шифрование, подтверждение подлинности и сохранение неизменяемой истории — и прямо говорит, что наличие шифрования само по себе не выполняет требований защиты. Здесь каждая задача решена своим механизмом, и каждый механизм проверяется своим тестом.

## 1. Модель угроз

| угроза | кто | механизм | проверка |
|---|---|---|---|
| Подмена результата контроля задним числом через приложение | пользователь с доступом | журнал только дописывается; решение — новая запись с автором | `test_controller_decides_and_raw_signal_stays` |
| Правка записи в базе обычным SQL | администратор БД | триггер в СУБД запрещает UPDATE, DELETE и TRUNCATE (PostgreSQL), UPDATE и DELETE (SQLite) | `test_update_and_delete_are_prevented` на обеих СУБД |
| Правка записи в обход защиты СУБД (снятие триггера владельцем базы) | владелец базы | цепочка хешей и подпись пакета | `test_bypass_changes_are_detected`, сценарий 08 |
| Правка с пересчётом всех хешей | владелец базы без ключа подписи | подпись последней записи пакета не сходится | `test_rewriting_the_whole_chain_breaks_the_signature` |
| Отрезание последних записей | владелец базы | подписанный якорь вне базы | `test_tail_truncation_is_caught_by_anchor` |
| Чтение данных из базы или её копии | владелец базы, похититель копии | AES-256-GCM, ключ вне базы и кода | `test_payload_is_encrypted_at_rest` |
| Подделка пакета событий от источника | сеть цеха | подпись пакета HMAC-SHA256 ключом источника | `test_signed_batch_from_edge_source` |
| Превышение прав | пользователь | права ролей в шине безопасности; отказ пишется в журнал | `test_only_controller_confirms` |
| Будущий квантовый противник против подписи истории | долгосрочная угроза | гибридная подпись Ed25519 + ML-DSA-65 | `test_hybrid_signature_needs_both_halves` |
| Потеря или вывод из оборота ключа | эксплуатация | смена ключа без перешифрования; недоступный ключ не мешает проверке подлинности | `test_rotation_and_profile_change_keep_old_records_verifiable`, `test_unavailable_key_blocks_reading_but_not_verification` |

Вне модели: злоумышленник, у которого одновременно есть права владельца базы и секретные ключи, может переписать историю целиком. Защита от него — отправка якоря во внешнюю систему, которой он не владеет (MES, 1С, отдельный сервер аудита); это описано как развитие.

## 2. Формат защищённой записи

Требование раздела 6.3 — по записи можно определить всё, что нужно для выбора механизма, не раскрывая секретов. Открытый заголовок записи:

| поле | смысл |
|---|---|
| `format_version` | версия формата записи, сейчас `zd-record/1`; не связана с версией контракта событий |
| `profile_id` | криптографический профиль, например `hybrid-pq-v1` |
| `key_id`, `key_version` | идентификатор и версия ключа |
| `mechanism` | применённые механизмы словами: `AES-256-GCM + Ed25519 & ML-DSA-65 (FIPS 204), SHA-384` |
| `nonce` | открытый параметр расшифрования |
| `kind`, `ref_id` | вид записи и связь с исходным событием или карточкой |
| `prev_hash`, `record_hash`, `signature` | цепочка и подпись |

Заголовок целиком входит в дополнительные данные AEAD: подмена заголовка без подмены шифротекста делает запись нерасшифровываемой. Секретные ключи не входят ни в запись, ни в код, ни в демонстрационный набор — они создаются при первом запуске в `var/keys` с правами только для владельца.

## 3. Профили

| профиль | шифрование | подпись | хеш | назначение |
|---|---|---|---|---|
| `classic-v1` | AES-256-GCM | Ed25519 | SHA-256 | совместимость, быстрый профиль |
| `hybrid-pq-v1` | AES-256-GCM | Ed25519 **и** ML-DSA-65 — обе части обязаны сойтись | SHA-384 | по умолчанию; долгосрочная защита истории |

Гибридная подпись устроена по образцу составных подписей IETF LAMPS: подделка требует взломать одновременно эллиптическую кривую и решётки. Шифрование — симметричное AES-256, которое квантовый противник ослабляет лишь квадратично, поэтому постквантовый механизм нужен именно в подписи: история должна оставаться доказательством годами.

**ГОСТ-профиль.** Формат уже несёт идентификатор профиля, поэтому профиль `gost-2012` (шифрование «Кузнечик», подпись ГОСТ Р 34.10-2012, хеш «Стрибог») добавляется как ещё одна запись в `PROFILES` без смены формата записи. В MVP он не реализован: сертифицированное СКЗИ для закрытого контура выбирается заказчиком, а открытые реализации ([pygost](https://github.com/mosquito/pygost), [gostcrypto](https://pypi.org/project/gostcrypto/)) несертифицированы. Российские постквантовые подписи («Шиповник», «Гиперикум») пока проекты ТК 26 — профиль под них появится после принятия стандарта.

## 4. Смена ключа и профиля

- Новый ключ выпускается командой `uv run python scripts/keys.py rotate [--profile …]`, кнопкой на экране «Журнал и защита» или сменой `security.crypto_profile` в конфигурации (новый ключ нового профиля создаётся при запуске).
- **Старые записи не перешифровываются.** Они остаются доказательством ровно в том виде, в каком были сделаны, и проверяются своим профилем и ключом. Миграция, которая молча перезаписывает историю, противоречит самой цели журнала.
- Прежние ключи переводятся в статус `retired`: ими не подписывают новое, но проверяют и расшифровывают старое.
- **Недоступный ключ.** Если секретная часть ключа утрачена или выведена из оборота, записи этого ключа не расшифровываются и помечаются `key_unavailable`, но их подпись проверяется по открытой части. Подлинность истории остаётся доказуемой и там, где читать её уже нельзя.

Данные для проверки, которые требует постановка, — записи до и после смены ключа и профиля, изменённый пакет, сценарий недоступного ключа — готовит и сразу проверяет `uv run python scripts/crypto_demo.py`: он печатает профиль, ключ и механизм каждой записи, затем показывает, что запись недоступного ключа не читается, но её подлинность проверяется, а изменённый пакет обнаружен. Те же ситуации закреплены тестами `tests/test_ledger.py`.

## 5. Разграничение доступа

| роль | права |
|---|---|
| контролёр | читать; подтверждать, отклонять, назначать доп. проверку, закрывать; решать «оценка невозможна»; управлять эмуляцией |
| мастер участка | читать; решать по проблемам участка как контролёр (подтверждать, отклонять, назначать доп. проверку, закрывать, решать «оценка невозможна»); управлять эмуляцией и прогонами |
| технолог | читать; устанавливать причину подтверждённого несоответствия; выгружать; заводить станки; управлять эмуляцией |
| руководитель производства | читать; выгружать; создавать и менять линии и параметры экономики; управлять эмуляцией |
| администратор | читать; целостность, ключи, журнал критических действий, синхронизация с внешними системами, приём событий, выгрузка, управление линиями и эмуляцией, просмотр интерфейса глазами другой роли |
| edge-источник | только передавать события, подписывая пакет своим ключом |

Все проверки прав — в одной точке (`security/bus.py`). Критические действия и отказы в доступе записываются в тот же неизменяемый журнал с автором и подробностями.

Пользователи и роли хранятся в базе. Пароль задаётся командой `scripts/keys.py password <пользователь>`, вводится с клавиатуры и нигде не печатается; в базу ложится только хеш scrypt с солью (2^14, 8, 1). Ответ на неверный вход один на любой случай — «неверный пользователь или пароль», а сама попытка пишется в журнал критических действий. Токен доступа подписан HMAC-SHA256 секретом из хранилища ключей и имеет срок действия. В демонстрационном режиме у условных пользователей пароль совпадает с логином (`administrator` / `administrator`), а под формой входа есть выбор роли, который подставляет логин и пароль в ту же форму. Вход при этом идёт тем же путём, что и в рабочем режиме: хеш, проверка, аудит. Это единственное упрощение, и оно выключается настройкой `security.demo = false`: пароль, заданный администратором, демонстрационный режим не перетирает, а выбор роли на экране входа исчезает. Реальные персональные данные не нужны: пользователи и операторы обозначены условными идентификаторами.

Временный публичный стенд Render запускается только с условными данными и с `security.demo = true`; его база и ключи удаляются при засыпании или перезапуске бесплатного сервиса. Финальный стенд VPS тоже публичен и работает в демонстрационном режиме, но его PostgreSQL и ключи лежат в отдельных постоянных томах; подробности в [deploy-vps.md](deploy-vps.md). Доступ по выбору роли на этих стендах не соответствует режиму производственной эксплуатации.

## 6. Защита передачи

Пакет от источника подписывается HMAC-SHA256 ключом этого источника (`X-Source-Id`, `X-Signature`); неподписанный или подписанный чужим ключом пакет отклоняется с кодом 401. В текущем Compose приложение общается с MES-эмулятором по HTTP внутри сети контейнеров; это соединение не зашифровано. Порт эмулятора не публикуется на хосте, поскольку его административные маршруты предназначены только для демонстрационного контура. При переносе компонентов на разные машины нужен настроенный и проверенный TLS между ними; обратный прокси перед публичным приложением сам по себе не защищает канал приложения к внешней системе. До настройки такого канала защищённый межузловой транспорт считать реализованным нельзя.

## 7. Как показать на защите

1. «Журнал и защита» → «Проверить целостность»: журнал цел, указаны число записей и номер якоря.
2. В терминале: `uv run python scripts/tamper.py S03-00010` — скрипт показывает, что обычное изменение запрещено, снимает защиту правами владельца базы, меняет один байт записи и возвращает защиту на место.
3. Снова «Проверить целостность»: указан номер изменённой записи и вид нарушения.
